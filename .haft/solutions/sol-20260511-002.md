# Solution Variants: dev/prod environment split

## Variant A — Shopify CLI theme environments (dev branch = unpublished theme)

Use Shopify CLI `theme push --unpublished` to maintain a separate unpublished theme in the same store. The "dev" theme is never published live. Preview via Shopify's theme preview URL (`?preview_theme_id=...`). Promote by publishing the dev theme.

**Strengths:**
- Zero cost — same store, no extra account
- Shares real store data (products, metafields, cart) — high fidelity
- Shopify CLI supports named environments in `shopify.app.toml` / `.env` — scriptable

**Weakest link:** Preview URLs are session-scoped and require a logged-in Shopify session to share — you cannot give an unauthenticated test URL to Lighthouse or synthetic checks without extra tooling (ngrok, Shopify theme share command).

**Risks:**
- Lighthouse/CI must handle auth or use `theme share` which generates a temporary public URL (expires 24h)
- Theme push/pull workflow requires discipline — easy to accidentally publish dev theme to prod
- No isolation for store config changes (shipping, payments, apps) — only theme-level separation

**Stepping stone:** Yes — establishes git-based theme workflow; enables GitHub Actions CI for theme linting/Lighthouse on PRs.

**Rollback:** Delete unpublished dev theme. No prod impact.

## Variant B — Separate free Shopify development store (Shopify Partners)

Create a free Shopify development store via Shopify Partners program. Sync theme code from prod repo. Dev store is permanently free, publicly accessible (with optional password), and fully independent.

**Strengths:**
- Full store isolation — test app installs, settings, checkout config without any prod risk
- Development stores are free indefinitely via Partners account
- Publicly accessible URL without Shopify session — Lighthouse and synthetic checks work natively
- Password-protect blocks search indexing without noindex gymnastics

**Weakest link:** Data fidelity — dev store has no real orders, customer data, or metafield population. Tests that depend on real catalog state (e.g., out-of-stock behavior, metafield-driven content) will miss prod-only conditions.

**Risks:**
- Theme sync is manual unless scripted (git push → `shopify theme push --store=dev-store`)
- App configurations diverge over time (dev store apps need separate installs/configs)
- Promoting to prod = `shopify theme push --store=prod` — one wrong flag = wrong target

**Stepping stone:** Yes — Partners account unlocks Shopify CLI app dev, custom app installs, and staging-grade testing for future feature work.

**Rollback:** Dev store is fully independent — tear down with no prod impact.

## Variant C — Shopify theme preview + Cloudflare Worker proxy (no extra store)

Use existing store's unpublished theme (same as A) but route a subdomain (`dev.koiiswim.com`) through a Cloudflare Worker that rewrites requests to append `?preview_theme_id=<id>` and injects a Shopify preview cookie. Makes dev accessible at a stable unauthenticated URL.

**Strengths:**
- Stable, bookmarkable dev URL without a second store
- Lighthouse and synthetic checks work against a real URL
- No cost (Cloudflare Workers free tier covers this)

**Weakest link:** Shopify preview cookies are domain-scoped and the Worker cookie injection approach is fragile — Shopify can change preview cookie behavior, and cross-domain cookie injection may break with browser security updates (SameSite policy).

**Risks:**
- Maintenance burden: Worker breaks when Shopify updates preview auth mechanism
- Not officially supported — relies on undocumented Shopify preview cookie internals
- SSL for `dev.koiiswim.com` subdomain requires Cloudflare proxying (minor, but one more config layer)

**Stepping stone:** Weak — solves the immediate URL problem but creates a brittle dependency. Does not open broader dev workflow improvements.

**Rollback:** Remove Worker route and subdomain DNS record. No prod impact.
