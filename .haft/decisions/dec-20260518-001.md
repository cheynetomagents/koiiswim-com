# Professional DevOps Pipeline (Hybrid)

## 1. Problem Frame

**Signal:** Currently, theme changes and app integrations are tested directly on the live koiiswim.com production store (or via preview themes), which is high-risk and lacks isolated data for destructive testing.

**Constraints:**
- Must be password protected to prevent SEO indexing/public access
- Must minimize or eliminate additional Shopify subscription costs (prefer Development Store)
- Theme must stay in sync with production for accurate testing

**Acceptance:** A functional Shopify staging environment exists (e.g., koiiswim-staging.myshopify.com) with production theme parity, password protection, and representative test data. Changes can be validated here before production deployment.

## 2. Decision

**Selected:** Professional DevOps Pipeline (Hybrid)

**Selection policy:** Prefer professional version control and full sandbox isolation over simpler but riskier theme-only duplication.

**Why selected:** Provides the best balance of safety (via isolation) and professional developer workflow (via Git) for a growing Shopify brand at $0 additional cost.


**Invariants:**
- Production 'main' branch MUST always match the live theme content.
- Staging store MUST remain password-protected at all times.

**Pre-conditions:**
- [ ] Shopify Partner account is active.
- [ ] GitHub repository for the theme is initialized and accessible.

**Post-conditions:**
- [ ] Staging store (koiiswim-staging) is operational and password-protected.
- [ ] GitHub repository is connected to both Production and Staging stores via the Shopify-GitHub integration.
- [ ] Shopify CLI is configured for all team developers.

**Admissibility:**
- NOT: NOT: Do not deploy to production without merging into 'main' branch in Git.
- NOT: NOT: Do not install unvetted apps directly on production without a staging soak test.

## 3. Rationale

**Counterargument:** Managing two separate stores increases administrative overhead; store-level settings (apps, shipping, navigation) must be manually duplicated, creating a risk of configuration drift.

**Selected variant weakest link:** Configuration Drift: The manual overhead of syncing non-theme settings (apps, navigation, shipping) between two stores is the most likely source of environment-specific bugs.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Professional DevOps Pipeline (Hybrid) | **Selected** | Provides the best balance of safety (via isolation) and p... |
| Duplicated Theme on Production Store (Data-Native Staging) | Rejected | Lack of isolation for apps and store-level settings; high risk of production leakage. |
| Infrastructure-as-Code (Terraform) Store Management | Rejected | Extreme technical complexity and incomplete Shopify API coverage for a team of this size. |

**Evidence requirements:**
- Successful 'theme push' from CLI to the Development Store.
- Successful automated GitHub deployment to the Production Store on merge to 'main'.

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| Automated Git-based deployment reduces manual 'cowboy' errors in theme updates. | incident_rate_during_theme_updates | < 5% failure rate |
| Development store sandbox prevents app-related production downtime. | outages_caused_by_new_apps | 0 incidents per year |

## 4. Consequences

**Rollback plan:**
Triggers:
- Critical deployment failure on 'main' that blocks storefront access for > 15 minutes.
- Git 'merge hell' where branches cannot be reconciled, blocking all deployments.
Steps:
1. Disconnect GitHub integration from the Production store.
2. Manually upload the last known-good theme ZIP archive to Production.
3. Revert local development to manual upload until CI/CD is repaired.

**Refresh triggers:**
- Team scales beyond 3 active theme developers.
- Multiple 'drift' incidents occur where staging fails to replicate a production bug.
